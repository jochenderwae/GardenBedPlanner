## Findings

Nine distinct, actionable findings below; each was filed as its own ticket
(numbers noted). Ordered roughly by how foundational/high-impact they are,
not by priority field (see each ticket for the priority actually set).

### 1. `index.css` still carries an unrelated starter-template stylesheet that actively fights the real app — [#141](https://github.com/jochenderwae/GardenBedPlanner/issues/141)

`frontend/src/index.css` has never been cleaned up from whatever scaffold
this project started from. It defines a second, entirely separate design
system in parallel with the real shadcn/Tailwind tokens:
- Its own color variables (`--text`, `--text-h`, `--bg`, `--accent-bg`,
  `--social-bg`, `--code-bg`, `--shadow`) with their **own** `prefers-color-scheme`
  media-query dark-mode switch — a second, independent dark-mode mechanism
  that has nothing to do with the `.dark` class-based token system
  (`--background`/`--foreground`/etc.) the rest of the app actually uses.
- `#root { width: 1126px; max-width: 100%; text-align: center; min-height: 100svh; ... }`
  and raw `h1`/`h2`/`code`/`.counter`/`#social .button-icon` element rules —
  none of which correspond to anything in this app (there's no `#social`
  element anywhere in `frontend/src`).

Concrete, verifiable consequences:
- `#root`'s `text-align: center` is why **9 separate files**
  (`AppShell.tsx`, `MobileShell.tsx`, `NavDrawer.tsx`, `Agenda.tsx`,
  `SeedGuide.tsx`, `PlantDetail.tsx`, `PlantsDatabase.tsx`,
  `SatelliteSections.tsx`, `PlantSearchList.tsx`) each carry an explicit
  `text-left` class to fight it back off. That's the effect of a global
  reset being patched over page-by-page instead of removed at the source —
  a real, checkable smell, not a hunch.
- The raw `h1 { margin: 32px 0; font-size: 56px; color: var(--text-h) }`
  rule applies to every literal `<h1>` in the app (`PlantsDatabase`,
  `PlantDetail`, `Agenda`, `SeedGuide` all render one). Tailwind's
  `mb-4`/`text-xl` classes win on `margin-bottom`/`font-size` (class beats
  element selector), but nothing in those pages sets `margin-top`, so each of
  those four `<h1>`s picks up an unintended 32px top margin from the
  leftover rule, and `color: var(--text-h)` is a value that was never wired
  into `--foreground`/the shadcn palette at all.

This is squarely a "design system genuinely needs cleanup" case per this
agent's own remit, not a five-minute frontend fix I should just do myself.

### 2. No shared `Input`/`Select`/`Textarea` primitive — 10 duplicate, already-drifted copies — [#142](https://github.com/jochenderwae/GardenBedPlanner/issues/142)

`components/ui/` has exactly three shadcn primitives: `button.tsx`,
`card.tsx`, `alert-dialog.tsx`. There is no `Input`. Instead, the exact same
Tailwind string —
`"w-full rounded-md border border-input bg-background px-2.5 py-1.5 text-sm outline-none focus-visible:border-ring focus-visible:ring-3 focus-visible:ring-ring/50"`
— is hand-copied as a local `const inputClass` in **10 different files**:
`BedPanel.tsx`, `AddBedForm.tsx`, `GardenPanel.tsx`, `EquipmentPanel.tsx`,
`PlantingPanel.tsx`, `PlantsDatabase.tsx`, `PlantSearchList.tsx`,
`FieldInput.tsx`, `LifeCycleFields.tsx`, `SatelliteSections.tsx`.

It's already drifted: `SatelliteSections.tsx`'s copy uses `px-2 py-1`
instead of `px-2.5 py-1.5` everywhere else — a real, current inconsistency
this duplication produced, not a hypothetical risk.

### 3. No shared accessible segmented-control/toggle-group primitive — 5 hand-rolled instances, no ARIA — [#143](https://github.com/jochenderwae/GardenBedPlanner/issues/143)

Five places implement a tab-like/radio-like exclusive-choice control as raw
`<button>` elements with manual `bg-primary`/`text-muted-foreground`
styling and no `role="tablist"`/`role="tab"`/`aria-selected` (or
`role="radiogroup"`/`aria-pressed`) — `Toolbar.tsx`'s mode toggle
(Edit/View), its Garden/Beds/Plants/Equipment tab switcher, its
Point/Row/Area placement-mode toggle, and `ShapeTypeToggle.tsx`'s
Rectangle/Polygon toggle (used from both `BedPanel` and `AddBedForm`). A
screen reader or keyboard user gets no indication these are a connected,
mutually-exclusive group beyond the visual color change — it reads as a row
of unrelated buttons.

### 4. Ad hoc modals with no focus trap, no Escape-to-close, no `aria-modal` — despite the correct pattern existing in the same codebase — [#144](https://github.com/jochenderwae/GardenBedPlanner/issues/144)

`AddBedForm.tsx`, `PlantsDatabase.tsx`'s inline `AddPlantForm`, and
`PlantPicker.tsx` each hand-roll `<div className="fixed inset-0 ..." onClick={onClose}>`
as their own modal/popover chrome, instead of the `Dialog`
(`@base-ui/react/dialog`, already used correctly in `NavDrawer.tsx`) or
`AlertDialog` (`components/ui/alert-dialog.tsx`, used correctly by
`BedPanel`'s delete-confirm dialogs, `ShapeTypeToggle`'s
rectangle-conversion confirm, and `OnboardingPrompt`) primitives already in
the app. Concretely missing versus those: a focus trap, Escape-to-close,
`role="dialog"`/`aria-modal="true"`, and focus return to the trigger on
close. This is a regression against the app's own established pattern, not
a case of "no primitive exists yet."

### 5. Tooltip pattern uses the bare `title` attribute — 53 occurrences across 8 files, not keyboard/touch accessible — [#145](https://github.com/jochenderwae/GardenBedPlanner/issues/145)

The recently-shipped "Add tooltips to every field" work (#125) and the
pre-existing editor panels both rely entirely on the native HTML `title`
attribute for field-level help text — `BedPanel.tsx` (10), `AddBedForm.tsx`
(3), `GardenPanel.tsx` (5), `EquipmentPanel.tsx` (4), `Toolbar.tsx` (3),
`SatelliteSections.tsx` (21), `LifeCycleFields.tsx` (2), `FieldInput.tsx`
(5) — 53 total. `title` tooltips aren't reliably triggered by keyboard
focus, aren't touch-accessible at all, and give no visual affordance that a
tooltip even exists — a sighted mouse user has to hover-and-wait to
discover one. Given the current CLAUDE.md accessibility bar ("keyboard
navigation... ARIA where semantic HTML isn't enough"), this doesn't clear
it despite being broad, deliberate, recent work.

### 6. `Snackbar` has no `aria-live`/`role="status"` — every autosave/undo confirmation is silent to screen readers — [#146](https://github.com/jochenderwae/GardenBedPlanner/issues/146)

`components/Snackbar.tsx`'s toast container has no live-region semantics.
Given `PlantDetail`'s `usePlantAutosave` and every satellite section's
add/remove-with-undo flow route every save confirmation through this same
component, a screen reader user currently gets zero indication a save
succeeded, failed, or that an Undo action is available — for what is this
app's *only* save-feedback mechanism on that page (fields autosave on
blur, there's no separate "Save" button/confirmation).

### 7. `Home.tsx`'s `min-h-svh` conflicts with `AppShell`'s already-viewport-bounded layout — [#147](https://github.com/jochenderwae/GardenBedPlanner/issues/147)

`AppShell` renders `header` (fixed height) + `main.min-h-0.flex-1.overflow-y-auto`
so the page never needs to scroll past the viewport. `Home.tsx`'s own
wrapper div sets `min-h-svh` (100% of the *full* viewport height) while
nested inside that already-constrained `main` — header height +
"at-least-100vh" content is provably taller than 100vh, so desktop's Home
screen picks up an unnecessary vertical scrollbar/overflow purely from this
mismatch. `Home` is the only page in the app using `min-h-svh` this way;
every sibling page uses ordinary `p-6`/`max-w-*` wrappers with no explicit
height constraint, relying on `AppShell`'s own scroll region correctly.

### 8. Mobile route set's own page-heading pattern is inconsistent with itself, and diverges from desktop for identical content — [#148](https://github.com/jochenderwae/GardenBedPlanner/issues/148)

Within the mobile shell alone: `MobileHome`, `MobileLogging`, and
`MobileNotifications` all use `Card`+`CardTitle` (renders at `text-base`,
16px) as their page heading, while `MobileAgenda` and `MobileSeedGuide` use
a bare `<h1 className="text-sm font-semibold">` (14px, outside any Card) —
smaller than even a `CardTitle` sub-heading, and visually the weakest
heading on the page despite being the page's own title. Separately, that
same string ("Agenda"/"Seed Guide") renders at `text-xl font-medium` (20px)
on the desktop routes for the exact same shared `AgendaView`/`SeedGuideView`
content — a 6px, two-weight swing for identical page titles isn't obviously
intentional versus copy-paste drift from whichever page was built first.

### 9. PWA manifest ships with `icons: []` — no home-screen icon configured at all — [#149](https://github.com/jochenderwae/GardenBedPlanner/issues/149)

`frontend/vite.config.ts`'s `VitePWA` `manifest` config has an empty
`icons` array. Per root CLAUDE.md, iOS Safari requires the PWA to actually
be *installed* via "Add to Home Screen" before push-notification prompts
will even fire — and push notifications are already live
(`MobileNotifications`/`useWebPushSubscription`, #46/#47). Without
manifest icons, most browsers' install-prompt heuristics won't fire at all
(commonly requiring at least a 192×192 and a 512×512 icon), and any install
that does happen shows a blank/generic icon on the home screen. This
undermines the one already-shipped feature (push) that depends on install
happening at all. Note: fixing this needs an actual icon asset produced
(192×192, 512×512, ideally a maskable variant) in addition to wiring the
manifest config — flagged here as a design/config gap, the icon asset
itself is a separate production step for whoever picks up the ticket.

## Not flagged (checked, found solid)

- Icon-only buttons consistently carry `aria-label` (`X` close buttons,
  edit/delete icon buttons throughout `BedPanel`, `EquipmentPanel`,
  `SatelliteSections`, `PlantsDatabase`, `NavDrawer`) — good, consistent
  pattern, no gaps found.
- `NavDrawer`'s use of plain `<Link>`s instead of `Dialog.Close` (to avoid
  `Dialog.Close`'s forced `role="button"` misannouncing a navigation link)
  is a deliberate, documented, correct choice.
- Labels throughout use the `<label><span>text</span><input/></label>`
  nesting pattern, which is valid implicit label association — no missing
  form labels found anywhere sampled.
- `OnboardingPrompt`/`BedPanel`/`ShapeTypeToggle`'s use of `AlertDialog`
  for destructive-action confirmation is correct and consistent where it's
  used (see finding #4 for where it's *not* used but should be).
- `SeedGuideView`'s urgency-badge color mapping (buy/sow/ok) reuses
  `bg-destructive/10 text-destructive` and friends from the real token
  palette rather than inventing new colors — good practice, no note beyond
  "this pattern could become a small shared `Badge` variant if a fourth
  urgency-style badge shows up elsewhere," which isn't worth a ticket on
  its own yet.
