# CLAUDE.md — data/etl

The plant-database ETL pipeline: `data/*.json` sources → `data/plants/<slug>.json`. Its own `uv` project (`data/pyproject.toml`), separate from `backend/`'s - this is a one-off batch tool, not part of the running app, and needs libraries (BeautifulSoup, jsonschema) the app doesn't. Run it from `data/`: `uv run python -m etl.run [--limit N]`.

## Pipeline stages

1. **Master list** (`run.build_master_list`) — `openfarm-crops-rescue`'s `crops.json` (340 records, one JSON array) seeds the canonical plant list; Homesteader Labs' crop files (`vegetables.json`, `herbs.json`, `fruits-annual.json`, `fruits-perennial.json`) extend it. Both are one-time bulk fetches, cached to disk (`etl/http_client.py`).
2. **Enrichment** (`run.enrich_plant`) — per plant: Permapeople and Trefle are queried by name/botanical-name (per-plant REST search - the only two sources that actually work this way); USDA PLANTS (one bulk CSV, fetched once, indexed by common name - see `sources/usda_plants.py`) and Wikipedia's companion-plants page (one bulk HTML fetch, parsed once - see `sources/wikipedia_companions.py`) are looked up against pre-built in-memory indexes, not queried per-plant.
3. **Merge** (`merge.py`) — per plant, every source's contribution is collected per field in priority order (the table in `data/CLAUDE.md`, top to bottom). A field with one distinct value across sources is unambiguous; 2+ distinct values is a real conflict.
4. **Resolve** (`ollama_resolve.py`) — conflicts go to local Ollama (`mistral-small:latest` by default - see the module docstring for why). Every resolution, win or lose, is appended to `data/conflicts_log.jsonl` as an audit trail (source, value, what was chosen, why) - this is where requirement 3's "keep all values, don't discard" actually lives, since the final export only keeps the resolved value.
5. **Export** (`export.py`) — builds the final `data/plants/<slug>.json`, validates against `data/plant.schema.json`, writes it.

## Requirement 4: interleaving sources to self-rate-limit - evaluated

The original idea: process plants in a staggered way across sources, so hitting each source is naturally spread out instead of bursty. Verdict: **not dumb, but the premise needed correcting, and it's a complement to hard rate limits, not a substitute for them.**

- Only 2 of the 6 sources (Permapeople, Trefle) are actually queried *per plant* - the other 4 are one-time bulk fetches (one GitHub file, one CSV, one HTML page, a handful of JSON files). There's nothing to "stagger" for a source you only ever hit once.
- For the two that are per-plant (`run.enrich_plant`), they *are* interleaved plant-by-plant: Permapeople then Trefle for plant N, then plant N+1, rather than all of Permapeople followed by all of Trefle. This does spread load, since each source's calls end up separated in wall-clock time by however long the other source's call took.
- But that spacing is incidental, not guaranteed - if both sources happened to respond instantly, interleaving alone wouldn't stop a burst. The actual rate-limit guarantee is the explicit per-source `RateLimiter` (`http_client.py`), a hard minimum interval enforced regardless of what else is happening. That's what to trust; the interleaving is a nice side effect, not the mechanism.
- The real payoff of processing plant-by-plant (enrich → merge → resolve → export, one plant fully at a time) turned out to be **requirement 6, not requirement 4**: it gives fine-grained per-plant checkpointing almost for free (`state.py`) - a crash mid-run only redoes the one plant that was in flight, not a whole source's worth of work. That's a better justification for this structure than the original rate-limiting motivation.

## Things worth knowing if you're continuing this

- **Identity matching is the trickiest part** (`matching.py`). Different sources call the same plant different things. The first real run surfaced a serious bug: matching by botanical name (genus + species) merged openfarm's own distinct entries for Acorn Squash, Zucchini, Pumpkin, Delicata Squash, Pattypan Squash, and Spaghetti Squash into one record, because they're all cultivars of *Cucurbita pepo*. Fixed by never fuzzy-matching a source's own listing against itself (`MasterList.add_distinct`) - fuzzy matching (`MasterList.add`/`find`, common-name-first, botanical-name-fallback) is only for folding one source's records into another's. If you add a new master-list-contributing source, use `add_distinct` for its own listing, `find`/`add` only when checking against what's already there.
- **Trefle's JSON shape is deeper than its own docs field list implies** (`sources/trefle.py`). `family`/`genus`/`growth`/`edible*` all live under `main_species`, not at the top level - the top-level `genus`/`family` keys are link-summary objects (`{id, name, slug, links}`), not the plain strings they look like. Bit the first real run (schema validation failure); fixed and commented in the source, but if Trefle's API changes, re-verify against a real cached response in `data/.cache/trefle/` before trusting the docs page alone again.
- **`OLLAMA_HOST` is a trap on this machine.** Ollama's own server reads a system-wide `OLLAMA_HOST` env var (here, `0.0.0.0` - a bind address, not a URL), and pydantic-settings picked that up instead of this package's own default, producing a scheme-less URL that `httpx` rejected. Fixed via an explicit `ETL_OLLAMA_HOST` alias in `config.py` (avoids the collision) plus a validator that adds `http://` if a scheme is still missing (belt and suspenders). Don't rename that setting back to plain `OLLAMA_HOST`.
- **Ollama's structured-output `format` must be typed per-field, not a bare `{}`.** An unconstrained `"resolved_value": {}` schema was read by the model as "produce a nested object", returning `{"full_sun": true}` instead of `"full_sun"` for a `sun_level` conflict. `ollama_resolve._FIELD_VALUE_TYPES` maps every resolvable field to its real JSON type/enum now - add new fields there if you add more to the schema.
- **Coverage is intentionally partial.** `composting_needs`, `fertilizer_needs`, `needs_wind_cover`, `needs_rain_cover`, `seed_info.*`, and `bedding_needs` have zero source coverage (see `data/CLAUDE.md`'s "Fields still needing a source") - the ETL will simply never populate them from the current source list, which is expected, not a bug.
- **List-field conflicts (`pest_interactions`, `periods`, `bedding_needs`) don't get full LLM resolution**, unlike scalars and companions - see `export.py`'s comments for the simpler fallback heuristics used there (highest-priority source wins, or widest-range union). Revisit if this turns out to matter in practice.
- Not yet built: the import script that upserts `data/plants/*.json` into Postgres (step 5 of the plan in `data/CLAUDE.md`). The ETL's job stops at producing validated JSON files.
