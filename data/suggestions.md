# Data Engineer Suggestions

Ideas the `data-engineer` agent has noticed for improving the data or its structure. The agent may append to this list but may not act on these itself or move them into `task_queue.md` - that's the user's call.

- 2026-07-19: **`growth_habit` field, for whoever builds the backend/frontend side.** Added `growth_habit` to `data/plant.schema.json` and populated it on 349/359 `data/plants/*.json` (10 logged to `data/growth_habit_unmatched.jsonl` as not confidently categorizable - see below). It's a closed 5-value enum: `upright` / `spreading` / `climbing` / `rosette` / `tree` / `null` - full definitions and reasoning are in the schema's own `description` for the field and in `data/etl/populate_growth_habit.py`'s module docstring, worth reading before wiring this up since the category boundaries are judgment calls (e.g. `spreading` deliberately merges "low woody bush" and "ground-sprawling vine" into one bucket - both need "wide, low canopy" rendering, not "tall and narrow"). This needs a matching `backend/app/models/plant.py` column + Alembic migration + API field + frontend rendering logic in the Konva bed editor - all explicitly out of this agent's data/-only scope. Distribution across the 349 populated plants: upright 136, spreading 78, tree 57, rosette 44, climbing 34.

- 2026-07-19: **Two real `botanical_name` data-quality bugs found while spot-checking `growth_habit` inference declines.** `data/plants/watermelon.json` has `botanical_name: "Dischidia ovata"` - an unrelated tropical epiphytic vine (family Apocynaceae), not a watermelon (should be `Citrullus lanatus`). `data/plants/ferry-morse-contender-bush-bean.json` has `botanical_name: "Acacia maconochieana"` - an Australian wattle tree, not a bean (should be `Phaseolus vulgaris`). Both look like a source (likely Trefle, given the pattern seen elsewhere in this pipeline of fuzzy species-name matching going wrong on ambiguous/cultivar common names - see `data/etl/CLAUDE.md`'s "Identity matching is the trickiest part") matched the wrong species during the original ETL run. Caught because Ollama correctly declined to infer a `growth_habit` for both once given the (wrong) botanical name + description, rather than because anything flagged it directly - worth a dedicated data-quality pass (e.g. cross-checking `family`/`genus` against `botanical_name`'s genus for every plant) rather than assuming this is the only pair.

- 2026-07-19: **No dedicated "sour cherry" (`Prunus cerasus`) plant record.** Root `CLAUDE.md`'s garden has a real sour cherry tree, but `data/plants/` only has a generic `cherry.json` (`botanical_name: Prunus avium`, sweet cherry) whose text also discusses sour varieties, plus `rainier-cherry.json` (a specific sweet-cherry cultivar - wrong species). Used the generic `cherry` record as the closest match in `data/example_garden.json`'s "Sour Cherry Tree" bed; a real `Prunus cerasus` record would be more accurate if anyone wants to add one (Homesteader Labs / Trefle / USDA PLANTS could all plausibly have it, wasn't checked).

- 2026-07-19: **`data/plants/cherry.json`'s `height_cm: 1500` looks like a units/data error** (15m - too tall for a garden fruit tree; standard/dwarf sour or sweet cherry trees are typically 200-500cm). Not fixed here (didn't want to guess a replacement value or touch a field outside this task's scope) - worth checking against the original source (openfarm-crops-rescue per its `data_sources` entry) and correcting or nulling it.

- 2026-07-19: **`data/growing_info_interesting_log.jsonl` has 611 entries worth a deliberate review pass.** This is the growing_info pipeline's "surface anything that doesn't map to an existing field" output (see `data/CLAUDE.md`'s `growing_information` section, pass 4 - "surface"), now fully populated since task 3 finished (140/140 plants). Skimmed it while closing out task 3 - looks like a genuine mix of things worth turning into real fields/entries eventually (specific pest-timing advice, companion-adjacent planting-order tips like "plant summer squash at the same time as cucumbers/cantaloupes for pollination timing") and things that are just narrative color not worth structuring. Also worth reading alongside it: `data/growing_info_crosscheck_log.jsonl` (104 entries, mostly old-book-era spacing in feet not matching modern cm values in structured fields - looks like genuine historical-vs-modern-practice drift, not extraction bugs, but a human should eyeball a sample to confirm). Neither log was acted on here - that's a deliberate, larger review task, not a small fix.

- 2026-07-19: **`companions[].companion_slug` sometimes references a slug that doesn't match any real plant file, just a near-miss** (e.g. `basil.json` lists `pepper-bell` as a companion, but the real file is `bell-pepper.json`; `zucchini.json` lists `french-marigold`, but the real file is `african-marigold.json`). Noticed while checking `data/example_garden.json`'s bed assignments for companion conflicts - didn't block anything (no *bad* relationship was missed, since the checker only needs `bad` entries in both directions to catch a real conflict, and none of these mismatches were `bad`), but it means a "does X conflict with Y" check can silently miss a `good` OR `bad` relationship if the counterpart's slug doesn't line up. `backend/app/scripts/import_plants.py` already skips dangling `companion_slug` references at import time (per its own history, see git log `ab119c9`) rather than failing import, so this is a known category of issue, not a new one - flagging in case a slug-normalization/alias pass is ever worth doing across `data/plants/*.json`.
